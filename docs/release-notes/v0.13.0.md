# Wealth Watcher v0.13.0

## Highlights

- Adds flexible per-connection integration polling schedules: every-N-minutes, five-field cron, hourly at a selected minute, hourly on the hour, daily at a selected time, or weekly at a selected weekday and time.
- Keeps Dashboard and History on one shared aggregate-period selection. Choosing Day, Week, Month, 3 Months, Year To Date, or MAX on either page updates the other page and is retained as a browser-local preference.
- Applies scheduled polling according to the API host's local time while retaining the existing optional market-hours gate for polling connections.

## Fixes

- Reloads Dashboard and History data when the selected aggregate period changes or a page is revisited with data for an older period, avoiding stale cross-page charts and summaries.
- Preserves the existing interval update path and browser-demo response shapes while exposing the new schedule fields through the integration API and UI.
- Refreshes the supported toolchain and provider dependencies, including .NET SDK 10.0.401, Vite 8.3.0, SnapTrade.Net 6.0.20, and the aligned .NET test/runtime packages.
- Adds regression coverage for schedule validation and due-time evaluation, shared-period persistence and routing, integration controls, and partial demo-history boundaries.

## Upgrade notes

- A database migration is required. API startup applies `AddIntegrationPollingSchedules`, adding the persisted schedule fields and backfilling each existing connection's schedule value from its current `PollingIntervalMinutes`. Existing connections therefore continue with the same every-N-minutes cadence unless you change them in Integrations.
- Back up PostgreSQL and the configured `CONFIG_PATH` Data Protection key directory before updating; back up the relay data directory as well when webhook delivery history matters. No manual data conversion is required after the migration.
- No new environment variable or deployment configuration change is required (`requiresConfigurationChange: false`). Advanced schedules are optional per connection, provider minimum polling intervals still apply to fixed-minute schedules, and wall-clock schedules use the API host's local time rather than the browser's time zone.
- The new browser-local aggregate-period preference does not require a data migration. For rollback, restore the previous API and web image tags or immutable digests and retain the verified backups. The schema change is additive; do not run a destructive schema downgrade as part of an image rollback.

## Known issues

- Wall-clock polling schedules follow the API host's local time and do not currently offer a separate per-connection time-zone setting; review the host time zone and daylight-saving behavior when configuring cron, daily, or weekly schedules.
- The application remains intended for a local or trusted network and has no built-in authentication, authorization, or tenant isolation.
